# Field

> The label, description, action, and error layer every control in this package is built on. Wrap any control and it joins the validation graph.

Use Field when you want to:

- Put a `label` and `description` on a control that doesn't take them directly — either takes any node, and one that renders nothing (`false`, `null`, `""`) paints no chrome. They render inside a `<label>` and a `<span>`, so stick to inline content
- Share one label across several controls — the inputs keep their own `name`s and the field supplies the heading. A `required` field makes every `FieldControl` or `InputControl` inside it required, so pass `required={false}` on any that are optional
- Put an `action` at the end of the label row — any node, including a button. `FieldHint` is ready-made content for it: a quiet `text` aside, with an optional `icon` before it. It is static, with nothing to hover or open, so longer guidance belongs in `description`. The action sits at the row's end and holds its width, so a long label wraps beside it rather than under it. An action taller than the label row, such as an `xsmall` button, grows the row instead of overlapping the label or the control. In a grid of side-by-side fields, a wide action can drop to its own line and push its control below its neighbours'; keep actions short there
- Scale the chrome with `size` — the label, description, and error take the same `--forms-size-*-font-size` the control itself reads, so they can't drift from the text inside it, and the gap stacking them tightens to match. Every control forwards its own `size`, so `<Input size="small" label="Email" />` already reads as one piece
- Show the error in the description's place — while the field is invalid the message replaces the `description` beneath the control, and the description comes back once the error clears. With no description, the error takes the same slot. The control is described by whichever one is showing: the hidden description is unmounted, not just hidden, so its id leaves the control's `aria-describedby`
- Validate with `validate` (return the message, or `null` when the value passes) and decide when it runs with `validationMode`
- Show an error owned outside the field, such as a form library's or a server's, with `invalid` and `ErrorProps={{ match: true, children: message }}`. `match: true` shows the message whatever the control's own validity says, and the control takes `aria-invalid`. With no message (`children` empty or `undefined`), `match: true` defers to the field's own validity, so the description stays
- Mark the whole field `required` or `disabled` — both reach the control, not just the label. `required` stamps `data-required` on the root, and a `FieldControl` or `InputControl` inside falls back to it unless it sets its own; a nested field starts unrequired. Other composed parts, such as `NumberFieldInput` or `SelectRoot`, don't read it, so pass `required` to them directly. A custom control rendered through `FieldControl` with `render` picks it up

A field with no label, action, or description paints no chrome and adds no layout: the control sits exactly where it would alone while still joining the field's validation graph.

Give the field a `name` and a surrounding [`Form`](../form/README.md) publishes the matching entry of its `errors` map onto it — the same path a server response takes. Slot overrides (`RootProps`, `LabelProps`, `DescriptionProps`, `ErrorProps`, `ActionProps`) reach the individual parts when a top-level prop isn't expressive enough. `LabelProps` and `DescriptionProps` take no `children`, since their content is `label` and `description`; the same holds for `FieldRow`. When a top-level prop and `RootProps` set the same key, the top-level prop wins. `ActionProps` is a part slot rather than the root, and `ActionProps.children` wins over `action` the same way it does on [`Card`](../../../cards/src/card/README.md).

`FieldRoot`, `FieldControl`, `FieldItem`, `FieldValidity`, `FieldLabel`, `FieldDescription`, `FieldError`, `FieldAction`, and `FieldHint` are exported for composition, along with `FieldRow` — the shared label row that [`Checkbox`](../checkbox/README.md), [`Radio`](../radio/README.md), and [`Switch`](../switch/README.md) sit in. The row swaps its error and description the same way Field does. `FieldControl` is a bare Base UI input for wiring your own control into a field; `render` swaps the element (`<FieldControl render={<textarea />} />`).

`FieldRoot` renders a `Stack`, so `RootProps` and a bare `FieldRoot` take its layout props (`gap`, `p`, `ax`, `ay`, `w`, ...) alongside Base UI's. It stretches its children across the field (`ax="stretch"`) unless you pass `ax`. It has no default `gap`: the field's `size` tier sets one, and a `gap` you pass pins it. A `render` of your own replaces the `Stack`, so layout props passed beside it reach your element as plain attributes.

Additional props are forwarded to the underlying Base UI [Field](https://base-ui.com/react/components/field).
